# PulseCart: Software Requirements Specification (SRS)

**Version:** 1.0 (draft)\
**Author:** Jatin Yadav\
**Date:** 27 October 2026\
**Status:** Draft for implementation

## 1. Introduction

### 1.1 Purpose

This document specifies the requirements, scope, architecture and implementation approach for **PulseCart**, a flash-sale marketplace with a live operations dashboard. It is the single reference for what will be built, what will not, and how.

### 1.2 Project goals

PulseCart is a portfolio and practice project. Its goals are:

1. Demonstrate production-style use of **OAuth with Passport**, **MongoDB aggregation pipelines**, **Redis caching** and **Socket.IO real-time communication**.
2. Handle realistic scale: millions of orders and thousands of concurrent users, validated with load tests.
3. Produce measurable, graph-ready evidence (latency, throughput, correctness under contention) for a README and demo.

### 1.3 Scope

PulseCart lets customers browse products and buy limited-stock items during timed flash sales. Sellers manage listings and see their sales. Admins watch a live dashboard and analytics. The system must never oversell stock, even under heavy concurrent load.

### 1.4 Definitions

| Term | Meaning |
| --- | --- |
| Flash sale | A time-boxed sale on a product with limited stock and a discounted price |
| Reservation | A temporary hold on stock while a buyer completes checkout (TTL-based) |
| Hot key | A cache or database key receiving disproportionate traffic |
| p95 / p99 | 95th / 99th percentile response time |
| SRS | Software Requirements Specification |

## 2. Overall Description

### 2.1 Product perspective

A web application with a React frontend, a Node.js API, MongoDB as the system of record, and Redis as the fast path for caching, counters, sessions, rate limiting and real-time fan-out.

### 2.2 User classes

| Role | Capabilities |
| --- | --- |
| Guest | Browse products, view sales, search |
| Customer | Everything a guest can, plus cart, reserve stock, checkout, order history, live order status |
| Seller | Manage own products and flash sales, view own sales analytics, receive live order notifications |
| Admin | Manage users and roles, view the live ops dashboard and full analytics, moderate listings |

### 2.3 Operating environment

- Node.js 22 LTS (or current LTS), TypeScript
- MongoDB 7+ (replica set, required for transactions and change streams)
- Redis 7+ (single node for development, optional Sentinel or Cluster later)
- Docker and Docker Compose for local and demo environments
- Modern evergreen browsers

### 2.4 Assumptions and constraints

- Single-developer project: favour simple, well-understood tools over exotic ones.
- Payments are simulated (no real money).
- Load is generated by the author's open-source traffic tool plus k6 and Artillery.
- Runs on a single machine or small VM for the demo; horizontal scaling is shown with two API instances.

## 3. System Architecture

### 3.1 Style

A **modular monolith** with clear module boundaries (auth, catalog, inventory, orders, analytics, realtime). This gives most of the benefit of microservices (separation, testability) without the operational cost. Modules communicate through in-process interfaces and an internal event bus, so any module can later be extracted.

### 3.2 Components

| Component | Responsibility |
| --- | --- |
| **Web client (React + Vite)** | Storefront, seller console, admin dashboard, Socket.IO client |
| **API (Node + Express/Fastify, TypeScript)** | REST endpoints, Passport auth, validation, business logic |
| **Realtime gateway (Socket.IO)** | Authenticated websocket connections, rooms, event broadcast |
| **Worker (BullMQ)** | Background jobs: order emails, reservation expiry, cache warming, analytics rollups |
| **MongoDB** | Users, products, sales, orders, events; aggregation analytics |
| **Redis** | Sessions, cache, stock counters, rate limits, leaderboards, pub/sub, Socket.IO adapter, job queues |
| **Nginx** | Reverse proxy and load balancer in front of multiple API instances (sticky sessions for websockets) |
| **Prometheus + Grafana** | Metrics and dashboards |

### 3.3 Key data flows

1. **Read path:** client calls the API, the API checks Redis, on a miss it queries MongoDB and stores the result with a TTL.
2. **Purchase path:** reserve stock atomically in Redis, create a pending order in MongoDB, confirm payment (simulated), finalise stock, publish an event.
3. **Real-time path:** domain events are published to Redis pub/sub, and the Socket.IO Redis adapter delivers them to clients on any API instance.

## 6. Non-Functional Requirements

### 6.1 Performance targets

| ID | Target |
| --- | --- |
| NFR-PERF-1 | Cached product detail: p95 under 50 ms at 2,000 requests per second |
| NFR-PERF-2 | Cached analytics endpoints: p95 under 50 ms; uncached p95 under 2 s on 2M+ orders with indexes |
| NFR-PERF-3 | Reserve-stock endpoint: p99 under 100 ms at 5,000 concurrent buyers |
| NFR-PERF-4 | Dashboard push latency under 500 ms from event to browser |
| NFR-PERF-5 | Support at least 5,000 concurrent Socket.IO connections across two instances |

### 6.2 Correctness and reliability

- **NFR-REL-1:** zero oversell. In a test of 10,000 buyers for 100 units, exactly 100 orders are confirmed.
- **NFR-REL-2:** no duplicate orders on retry (idempotency keys).
- **NFR-REL-3:** graceful degradation. If Redis is unavailable, reads fall back to MongoDB and the sale endpoint fails closed with a clear error rather than overselling.
- **NFR-REL-4:** graceful shutdown that drains HTTP and websocket connections.

### 6.3 Security

- OAuth state parameter and PKCE where supported; callback URLs allow-listed.
- Cookies: HTTP-only, Secure, SameSite=Lax; CSRF protection on state-changing session routes.
- Input validation with a schema library (Zod) on every endpoint and socket event.
- Helmet security headers, strict CORS, and request body size limits.
- NoSQL injection prevention (reject operator keys in user input) and parameterised query construction.
- Secrets in environment variables, never committed; `.env.example` provided.
- Dependency auditing in CI.

### 6.4 Maintainability and quality

- TypeScript strict mode, ESLint and Prettier, conventional commits.
- At least 70% unit test coverage on business logic; integration tests for critical flows.
- Every module has a README section describing its purpose and public interface.

### 6.5 Observability

- Structured JSON logs (Pino) with a request ID propagated through logs, jobs and socket events.
- Prometheus metrics: request duration histograms, cache hit ratio, queue depth, websocket connections, stock counter operations.
- Optional distributed tracing with OpenTelemetry.

## 7. Data Model

### 7.1 MongoDB collections

| Collection | Key fields | Indexes |
| --- | --- | --- |
| `users` | `_id`, `email`, `name`, `role`, `providers[]` (provider, providerId), `createdAt` | unique `email`; `providers.provider + providers.providerId` |
| `products` | `_id`, `sellerId`, `title`, `category`, `price`, `rating`, `stock`, `status`, `createdAt` | `category + price`; `sellerId`; text index on `title` |
| `sales` | `_id`, `productId`, `salePrice`, `allocated`, `sold`, `startsAt`, `endsAt`, `perUserLimit` | `startsAt + endsAt`; `productId` |
| `orders` | `_id`, `userId`, `items[]`, `total`, `status`, `idempotencyKey`, `createdAt` | `userId + createdAt`; unique `idempotencyKey`; `status + createdAt`; `items.productId + createdAt` |
| `events` | `_id`, `type` (view, cart, purchase), `userId`, `productId`, `ts` | `type + ts`; `productId + ts`; optional time-series collection |
| `rollups_daily` | `date`, `category`, `revenue`, `units` | unique `date + category` |

### 7.2 Modelling principles

- **Embed what is read together** (order line items inside the order); **reference what grows unbounded** (events reference users and products).
- Use a **time-series collection** for `events` to get compression and fast time-range scans.
- Money is stored as integers in the smallest unit (paise or cents), never floating point.
- Orders keep a **snapshot** of the product title and price at purchase time.
- Every index must be justified by a query and verified with `explain("executionStats")`.

### 7.3 Redis key design

| Purpose | Key pattern | Type | TTL |
| --- | --- | --- | --- |
| Sessions | `sess:{sid}` | string/hash | 7 days (sliding) |
| Product cache | `cache:product:{id}` | string (JSON) | 60 s plus jitter |
| Analytics cache | `cache:ana:{name}:{params-hash}` | string (JSON) | 5 min |
| Stock counter | `stock:{saleId}` | integer | until sale end |
| Reservation | `resv:{saleId}:{userId}` | string | 5 min |
| Purchase count per user | `bought:{saleId}:{userId}` | integer | until sale end |
| Rate limit | `rl:{scope}:{id}` | sorted set or counter | window length |
| Leaderboard | `lb:topsellers:{day}` | sorted set | 2 days |
| Idempotency | `idem:{key}` | string | 24 h |

Use a consistent prefix and a version segment (for example `v1:`) so cache formats can change without manual flushes.

## 9. Implementation Guide

This section explains how to build each capability using current best practice.

### 9.1 Project structure

A monorepo with npm or pnpm workspaces:

- `apps/api`: Node API and Socket.IO gateway (TypeScript)
- `apps/worker`: BullMQ workers
- `apps/web`: React + Vite client
- `packages/shared`: Zod schemas, types and constants shared by all apps
- `scripts/`: seed and load-test scenarios
- `infra/`: Docker Compose, nginx, Prometheus and Grafana config

Inside `apps/api`, organise **by feature module** (`auth/`, `catalog/`, `inventory/`, `orders/`, `analytics/`, `realtime/`), each with its own routes, service, repository and tests, rather than by technical layer.

### 9.2 OAuth with Passport

1. Register Google and GitHub OAuth apps and set callback URLs per environment.
2. Configure `passport-google-oauth20` and `passport-github2` strategies. In the verify callback, find the user by `providers.provider + providerId`, else by verified email, else create one with the `customer` role.
3. Use `express-session` with `connect-redis`; set `cookie: { httpOnly: true, secure: true, sameSite: 'lax' }` and regenerate the session ID on login to prevent fixation.
4. Serialise only the user ID into the session; load the user (with a short Redis cache) on each request.
5. Add an `authorize(...roles)` middleware and apply it per route.
6. For Socket.IO, share the session middleware with the engine (`io.engine.use(sessionMiddleware)`) and reject unauthenticated sockets in `io.use`.
7. Optional: add a JWT strategy with short-lived access tokens (about 15 minutes) and rotating refresh tokens stored hashed in Redis.

### 9.3 Stock reservation without overselling

The core correctness feature. Use a **Lua script** so that the check and the decrement happen atomically inside Redis:

```lua
-- KEYS[1] = stock:{saleId}, KEYS[2] = bought:{saleId}:{userId}
-- ARGV[1] = per-user limit
local bought = tonumber(redis.call('GET', KEYS[2]) or '0')
if bought >= tonumber(ARGV[1]) then return -2 end
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then return -1 end
redis.call('DECR', KEYS[1])
redis.call('INCR', KEYS[2])
return stock - 1
```

Flow:

1. Call the script. `-1` means sold out, `-2` means limit reached, otherwise the remaining count is returned.
2. On success, write the reservation key with a 5-minute TTL and publish `stock:update`.
3. On checkout, convert the reservation into a pending order. If payment fails or the TTL expires, a worker increments the counter back and publishes the update.
4. At sale end, a job reconciles the Redis counter with MongoDB `sold` and writes the final value.
5. Always load the initial counter from MongoDB when the sale starts, and treat MongoDB as the record of truth after reconciliation.

### 9.4 Idempotent checkout

1. The client sends an `Idempotency-Key` header (a UUID generated per checkout attempt).
2. The server does `SET idem:{key} processing NX EX 86400`. If the key already exists, return the stored result or a 409 while the first request is still running.
3. Also keep a unique index on `orders.idempotencyKey` as the last line of defence.
4. Use a MongoDB transaction when the order write and the sale `sold` update must succeed or fail together.

### 9.5 MongoDB aggregation pipelines

Guidelines:

- Put `$match` and `$sort` early so they can use indexes; project only needed fields.
- Use `$dateTrunc` for time bucketing and `$setWindowFields` for running totals and moving averages.
- Use `$facet` for the search page (results, category counts, price histogram) in one round trip.
- For very large reports, precompute with `$merge` into `rollups_daily` on a schedule, then query the rollups.
- Run `explain("executionStats")` on every pipeline and record documents examined versus returned.

Example, revenue by category per day:

```js
db.orders.aggregate([
  { $match: { status: 'paid', createdAt: { $gte: from, $lt: to } } },
  { $unwind: '$items' },
  { $group: {
      _id: { day: { $dateTrunc: { date: '$createdAt', unit: 'day' } },
             category: '$items.category' },
      revenue: { $sum: { $multiply: ['$items.price', '$items.qty'] } },
      units: { $sum: '$items.qty' } } },
  { $sort: { '_id.day': 1 } }
])
```

### 9.6 Redis caching strategy

| Technique | Where used |
| --- | --- |
| **Cache-aside** | Product detail and listing pages |
| **Write-through invalidation** | On product update, delete the product key and the affected listing keys |
| **TTL with jitter** | Add random seconds to every TTL to avoid synchronised expiry |
| **Stampede protection** | Single-flight lock (`SET lock:{key} NX PX 5000`) so only one request rebuilds a hot key; others wait or serve stale |
| **Stale-while-revalidate** | Analytics return the cached value immediately and refresh in the background |
| **Negative caching** | Cache "not found" for a few seconds to protect the database from repeated bad IDs |

Track hit ratio, evictions and memory in Prometheus, and set `maxmemory-policy allkeys-lru` for cache data.

### 9.7 Real-time with Socket.IO

1. Create the server with the **Redis adapter** (`@socket.io/redis-adapter`) so events cross instances.
2. Use **rooms** (`product:{id}`, `user:{id}`, `seller:{id}`, `admin`) and emit only to the relevant room.
3. Emit domain events from the service layer to an internal event bus; a single realtime module subscribes and translates events into socket messages. This keeps business logic free of socket code.
4. **Throttle** hot streams: collect stock changes and send at most a few updates per second per product; send dashboard ticks once per second.
5. Enable **connection state recovery** and have the client refetch state on reconnect.
6. Configure nginx with `ip_hash` or sticky cookies and websocket upgrade headers.
7. Prefer websocket transport only in production to avoid long-polling sticky-session problems.
8. Validate every incoming socket event with Zod and rate limit per socket.

### 9.8 Rate limiting

Implement a sliding-window limiter in Redis (sorted set of timestamps or a token bucket in Lua). Apply layered limits: strict on auth and reserve endpoints, relaxed on reads, plus a global per-IP limit. Return `429` with a `Retry-After` header and expose blocked-request counts as a metric.

### 9.9 Background jobs

Use **BullMQ** for: reservation expiry (delayed jobs), order confirmation emails (with retries and exponential backoff), analytics rollups (repeatable jobs), and cache warming before a sale starts. Make every job idempotent, and add a dead-letter queue and a small Bull Board UI for inspection.

### 9.10 Modern engineering practices

- **TypeScript end to end** with shared Zod schemas as the single source of truth for types and validation.
- **12-factor configuration** validated at startup (fail fast on missing variables).
- **Domain events** and an internal event bus for decoupling.
- **Dependency injection** by passing dependencies into module factories, which keeps tests simple.
- **Structured logging, metrics and tracing** from day one (Pino, prom-client, OpenTelemetry).
- **Graceful shutdown** on `SIGTERM` (stop accepting traffic, drain, close connections).
- **Containerisation** with multi-stage Dockerfiles and non-root users.
- **CI pipeline** (GitHub Actions): lint, typecheck, test, build images, dependency audit.
- **Feature flags** via environment config for optional extras such as JWT or rollups.

## 13. Acceptance Criteria

The project is complete when all of the following are demonstrated and documented:

1. Users can sign in with Google and GitHub, and role restrictions are enforced.
2. The flash-sale test with 10,000 virtual buyers and 100 units produces exactly 100 confirmed orders and zero oversell.
3. Retrying a checkout with the same idempotency key never creates a second order.
4. A heavy aggregation endpoint shows a measured improvement from caching (target: at least 10x faster at p95) with graphs.
5. An `explain` comparison shows an index changing a collection scan into an index scan.
6. The admin dashboard updates live and stays correct with events produced on either of two API instances.
7. Rate limiting blocks an abusive client while other clients see no degradation.
8. Killing Redis does not cause oversell, and the system recovers when Redis returns.
9. CI is green, and the README explains setup, architecture, trade-offs and results.

## 14. Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Redis and MongoDB stock counts drift apart | Wrong inventory | Reconcile at sale end; treat Redis as the live counter and Mongo as the record; log every adjustment |
| Cache stampede on sale start | Database overload | Pre-warm caches, single-flight locks, TTL jitter |
| WebSocket connections break behind the proxy | Dashboard stops updating | Sticky sessions, websocket-only transport, tested nginx config |
| Scope creep into extras | Project never finishes | Keep to must-have items first; extras behind feature flags |
| Load tests hit laptop limits | Misleading numbers | Record machine specs, run the generator on a separate process or machine, report relative improvements |
| Large dataset slows development | Slow iteration | Keep a small seed profile for development and a full profile for benchmarks |

## 15. Future Enhancements

Possible follow-ups after the core is complete: Redis Streams for durable event processing, change streams for cache invalidation, CQRS read models, OpenTelemetry tracing across API and workers, a Kubernetes deployment, and a real payment sandbox integration.
